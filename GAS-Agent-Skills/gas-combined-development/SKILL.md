# 组合开发模式技能

**外层分权制衡，内层集中执行；外层执行者就是内层指挥者。** 外层立规者、执行者、裁衡者平级；执行者在生效契约内组织集权团队，下辖内层执行者、审查者和监督者。内层接受成果后仍需外层独立裁衡，最终集成发布由同一执行者／指挥者承担。

本技能连接两个同级技能，不改变它们单独使用时的规则。它提供协作协议、记录模板和行为场景，不自带运行器、权限隔离或发布服务。

需要直观了解角色连接和实际启动方式时，查看 [架构图与 Codex 使用说明](references/architecture-guide.md)；左侧为架构，右侧为使用步骤，附可复制的启动提示词。

## 启动与适用边界

启用前读取本技能的 [组合协议](references/protocol.md)，以及同级 [分权技能](../gas-decentralized-development/SKILL.md) 和 [分权协议](../gas-decentralized-development/references/protocol.md)、[集权技能](../gas-centralized-development/SKILL.md) 和 [集权协议](../gas-centralized-development/references/protocol.md)。组合特例见 COM-01；未调整的规则按各自层级沿用。缺依赖先定位同一包内技能，仍不可读则报告缺失，只准备草案，不凭记忆声称完整启用。

适合同时需要独立定规／裁衡和统一实施指挥的跨模块任务。仅选择其中一种模式、普通单人修改或讨论概念时，不自动切换成组合模式。用户已选择组合模式后，在真实授权与宿主能力内启动，无需重复批准该选择。

默认主会话任外层执行者／内层指挥者；使用独立身份担任其他角色。主会话也可担任外层另一席，但须有真实工具支持执行者管理其内层团队。宿主父子关系不是治理上下级：主会话不能因持有工具就指挥或替换外层同席。

先核对现有修改、允许路径、验证入口、真实身份、通信、并发上限和总预算，登记 [运行与桥接模板](templates/run.example.json)。完整默认配置需要 **6 个不同身份、6 个并发席位（含主会话）**：外层三席加内层三个下属；双重身份只计一个人。更多内层执行者额外计数。宿主不足按 COM-06 降级，不绕过席位上限。

## 子 Agent 创建前的人类交互（AGENT-01）

每次新建、增补或替换子 agent，必须依次完成“配置弹窗 → 职责弹窗 → 人类明确答复 → 创建”。适用于所有角色及组合模式的内外两层；启用模式、已有开发授权或常规派工授权不能代替本次选择。可以批量展示，但必须逐个列出 agent，允许分别修改。不得先创建再补问。

1. **核对可用能力。** 同时检查创建工具与宿主的独立自定义 agent 配置能力，不只检查工具参数；按当前模型列表、推理强度和服务档位支持情况提供选择。选择 Fast 或发现创建工具缺少档位字段时，必须读取 [Fast 配置与回执核验](references/fast-service-tier.md)，核查独立 TOML／角色配置路径后才可判定不支持。模型、推理强度与服务档位是三个独立设置，不能用降低推理强度冒充 Fast。
2. **配置弹窗。** 使用客户端原生交互提问工具；当前支持时优先使用 `functions.request_user_input_async`，其他工具仅在其当前模式与用途允许时使用。分项提供模型、该模型支持的推理强度、服务档位选项，标出推荐项并允许自由回答；选项数量超过界面限制时分批展示。服务档位使用“默认档位（Default／Standard）”与“Fast 档位”，不使用“1 倍／1.5 倍”作为配置值。人类改变模型后重新核对强度和档位兼容性。不可用的档位须说明，不伪装成可执行选项；只有直接参数与独立角色配置两条路径均已核查且不可用时，才说明具体限制，让人类选择接受当前实际档位或暂缓创建，当前档位未知时明确标注未知，不称其为默认。
3. **保持活跃并等待。** 每次配置弹窗、职责弹窗和修改后再次确认，都进入下述“等待人类”流程。等待期间整个任务停在当前交互步骤，连不依赖该 agent 的后续工作也不推进。不兼容或不可用的选择须说明原因并重新提供可用选项，不静默替换。
4. **职责弹窗。** 配置确定后，再通过弹窗逐个展示 agent 的名称／角色、所选配置、目标、负责模块或路径、具体职责、交付物、验收标准和权限边界。提供“按当前职责创建”“修改职责后再确认”“取消创建”选项，并明确可直接自由输入职责修改。收到修改后更新职责并再次展示；只有人类明确接受最终版本才可创建。涉及模式角色边界冲突时说明冲突并由人类决定调整方案，不暗中改动模式。
5. **按最终选择创建。** 创建调用和任务提示必须与最终答复一致，通过当前接口支持的字段或获准的配置机制传递模型、推理强度及服务档位；没有服务档位参数时不向创建工具硬塞字段，也不把提示词中的 Fast 当作已设置。若显式覆盖配置与完整历史继承不兼容，使用接口允许的有限／空历史并在任务提示中补齐必要上下文。给实现者明确文件所有权，并说明共享工作区、保留他人修改。创建失败后若需改变配置或职责，重新弹窗，不擅自降级。
6. **记录与限制。** 在运行记录中保留每个 agent 的配置选择、最终职责、人类答复引用、实际创建参数、返回身份及未能验证的设置；尚未创建时不填虚假身份。原生弹窗不可用时，说明缺失并暂缓创建，等待交互能力恢复或人类明确允许替代方式；普通聊天说明不能冒充已完成弹窗。收到取消则不创建。此规则不为已创建 agent 在已确认职责内的普通后续派工增加审批。

### 运行位置：默认在 Codex 子 agent 列表展示

**所有子 agent 默认使用 Codex 客户端原生子 agent 创建与管理通道，并在当前任务的子 agent 列表中展示。** 本条约束 agent 会话的承载方式；agent 正常调用终端做构建、测试或其他工具操作不属于“放到 CLI 运行”。

- **原生列表优先。** 创建前核对原生子 agent 工具、角色加载与父子会话关联；创建后核对目标身份与客户端可发现记录。独立自定义 TOML／Fast 配置优先用于原生角色，不因创建工具缺字段或加载失败直接改用 `codex exec` 等独立 CLI 会话、后台进程或终端脚本托管 agent。普通聊天中列出名称、打开终端标签或另建普通会话，都不能冒充子 agent 列表展示。
- **需要 CLI 时先弹窗。** 在启动任何 CLI agent 前，必须通过客户端原生弹窗说明受影响角色、具体理由、已尝试的列表方式、CLI 的展示和管理差异，以及预期运行范围；提供“同意本次 CLI 运行”“不同意，继续尝试子 agent 列表”“暂停／取消创建”，允许自由回答。等待期间沿用保持活跃、不推进任务的规则。没有弹窗或未回复时不得启动，超时也不算同意。
- **人类同意。** 仅在答复覆盖的角色和范围内使用 CLI，继续遵守已确认的模型、强度、服务档位、职责、预算和全员就绪要求；不能把一个角色的同意扩大到全部团队。启动前在 Codex 客户端明确说明实际运行位置，创建后报告真实会话／进程身份、状态查看方式和控制入口，不声称已进入原生列表。
- **人类不同意。** 保留拒绝记录，继续尝试原生列表路线，检查角色注册与重载、配置作用域、所选角色、父子关联、工具返回错误及可用的原生重试／恢复方式；对已发现原因做相应修正，不以同样参数反复失败代替排查。不得因一次失败、等待较久、操作方便或 Fast 设置麻烦立即切换 CLI。
- **确实只能 CLI 的最终兜底。** 只有已取得前述弹窗答复、用户不同意后仍完成了当前环境适用的列表路径排查／修复／重试，并有可核对证据表明列表方式无法实现而 CLI 可行，才可按本规则的条件性兜底授权使用 CLI；无需把此前拒绝篡改成同意。启动前必须在 **Codex 客户端主会话** 明确列出失败证据、为何只能 CLI、将使用 CLI 的角色及查看／停止方式，运行记录注明“列表路径不可用后的 CLI 兜底”。未尝试或未知能力不能算不可能。用户若进一步明确“即使只能 CLI 也禁止使用”、要求暂停或取消，则服从该最新指令，保持等待，不启用兜底。
- **未就绪不得推进。** 原生路径须有可核对的列表关联／展示证据；CLI 路径须满足本条同意或严格兜底条件并已在客户端披露。把运行位置、实际身份、展示验证状态及弹窗答复计入完整团队就绪核对。无法确认列表展示或 CLI 条件未满足时保持 `WAITING_FOR_TEAM`，不虚构已显示、已同意或全员就绪。
- **能力边界。** 宿主硬性权限、并发和预算限制不因改用 CLI 失效；不得通过 CLI 绕过它们。本技能规定创建决策与披露流程，不能把未被客户端支持的 CLI 会话强制塞进原生列表。

### 全员就绪后统一启动

**所有计划中的子 agent 没有全部创建并就绪之前，禁止推进任务。** 本规则适用于集权、分权和组合模式；组合模式须同时覆盖外层与内层，不能仅外层建齐就开始工作。

- **先确定完整名单。** 创建前登记本轮全部角色、子 agent 数量及职责版本，逐个完成配置与职责弹窗确认。禁止把尚未创建的必需角色挪到“以后再建”以规避等待。名单如需删减或职责调整，须由人类明确确认，不能因创建失败自动缩减团队。
- **逐个创建，全部待命。** 每个创建提示都必须明确：“当前仅确认身份、配置与职责，回复就绪并等待全员就绪通知；不得开始任务执行。”创建调用成功返回真实身份且该 agent 已确认职责并报告就绪，才记为该成员创建完成；已发出调用、排队中、身份未知或尚未回复均不算。先创建好的子 agent 不能提前分析业务、改文件、测试、审查或发布。
- **只允许组建动作。** 屏障关闭期间，主会话和已创建的子 agent 仅可处理人员名单、配置选择、职责确认、创建／重试、就绪回执及必要的等待和状态记录，不推进任何业务任务，包括不依赖缺席成员的工作。组合模式中负责内层团队的执行者可以继续完成内层创建，但不能开始外层或内层业务工作；任一弹窗待答时仍按“等待人类”流程停在该步骤。
- **核齐后统一启动。** 按完整名单核对所有真实身份、最终确认记录和就绪回执，全部满足后才记录 `TEAM_READY`，向各成员发送对应名单与职责版本的启动通知，并进入业务流程；无需额外再问一次批准。该通知只是全员就绪事实，不改变三种模式原有的派工权与平级关系。任一成员失败、未确认或不可用时保持 `WAITING_FOR_TEAM`，不以其他成员就绪、时间已到或局部任务独立为由放行。
- **增补或替换重新等待。** 运行中决定新增或替换成员时，关闭全员就绪屏障并通知现有成员在最近安全点停住，不开启新的业务动作；允许正在进行且不能安全中断的动作到安全点，并如实记录。新名单全部创建并确认就绪后再统一恢复，不强杀进程制造“已暂停”。本规则优先于技能和协议中“继续不受影响工作”的一般条款；工具无法实现待命与统一恢复时报告限制并保持未就绪，不虚构屏障已生效。

### 服务档位：默认与 Fast

本技能中用户所说的“1.5 倍速”映射为 **Fast 服务档位**，“非 1.5 倍速”映射为 **默认档位**；倍速只是用户表达，不是接口参数，也不是对实际耗时的保证。

- Fast 在 Codex 配置中使用 `service_tier = "fast"`，官方配置说明将其映射为请求值 `priority`；实际调用始终按当前宿主接口接受的值填写，不混用配置值与请求值。
- 默认档位表示标准处理，不是“任意继承当前设置”。若宿主支持显式标准档位，按其接口设置；只有已核实继承结果为标准档位时才能省略。继承的是 Fast 时不得称为默认。不要为单个子 agent 擅自修改影响其他会话的全局配置。
- Fast 可以通过独立自定义 agent TOML 的顶层 `service_tier = "fast"` 设置，并在创建时选择该角色；无需依赖创建工具直接暴露服务档位参数。具体路径、完整示例与加载检查见 [Fast 配置与回执核验](references/fast-service-tier.md)。
- 区分配置意图、宿主会话确认与逐请求档位。宿主目标会话回执确认所选模型／强度及 `serviceTier: priority` 后，即可记录“该会话 Fast 配置已确认”，解除仅有意图的阻塞；不再要求不存在的 spawn 参数或固定提速证明。逐请求实际档位另以该轮响应为准，不把会话回执说成每轮都固定提速 1.5 倍。无宿主确认时如实记未验证，不自动更换选择。

映射依据：[Codex 配置说明](https://learn.chatgpt.com/docs/config-file/config-reference)；[OpenAI Fast mode](https://developers.openai.com/api/docs/guides/fast-mode)。模型与宿主支持范围以当前工具能力为准。

### 等待人类：保留弹窗，保持任务活跃，不推进

- **思考时间。** 每个弹窗默认预留至少 **30 分钟**，人类可指定更长时间。30 分钟是思考窗口，不是自动取消期限；届满仍未答复就延续等待。人类提前答复则立即处理，不必等满时长。
- **真正等待。** `functions.request_user_input_async` 返回只代表问题已发出，不代表用户已回答。保留同一待答弹窗；随后使用当前可用、能被新用户消息唤醒的等待工具。在支持 `clock.sleep` 的宿主中，每次调用 `clock.sleep({duration_ms: 60000})`，返回后检查实际用户消息，未取得本轮有效答复就再次等待。每轮最多 60 秒，避免一次长阻塞；工具返回、一次等待超时或无关消息均不解除等待。
- **禁止结束或越过。** 不因用户暂未点击发送 `final`、标记任务完成、自动取消、收起／替换弹窗，也不创建 agent、继续派工、实施、验收或发布。不用“等你答复”作为结束任务的最终答复；可以按宿主要求发送简短的等待状态说明，但不催促、不改变问题、不反复重开弹窗。这里的等待约束优先于本技能其他“继续不受影响工作”的一般规则。
- **有效答复。** 只接受针对当前问题的人类实际提交；预选、空答、未回复、过往选择均不算。仅回答部分配置时保留已答项，继续收集缺失项；“我还在想”“继续等”延长等待，无关消息不当成配置或职责确认。人类明确取消、暂停或改变任务时按其新指令处理；修改职责后对最终版本重新确认。
- **能力与恢复。** 不向提问工具添加不存在的超时或保活参数，不用忙循环、后台进程或定时任务冒充前台等待。当前工具无法设置客户端弹窗保留时长；技能约束的是 agent 的等待行为，不能保证界面持续显示或绕过宿主硬性时限／预算。若宿主确实强制中断，保存待答问题、已选配置和职责版本，记录 `WAITING_FOR_HUMAN` 而非完成；说明实际限制，恢复后从该步骤继续，已收到的有效答复不重复索取。仅确认旧弹窗已失效时才重新展示。

## 权责边界

```text
人类：目标、授权、预算与保留决定
          外层三方平级制衡
立规者  ←→  执行者  ←→  裁衡者
               ║ 同一身份、同一任期
            内层指挥者
         ┌─────┼─────┐
     内层执行者  审查者  监督者
```

| 角色 | 权力和交付责任 | 边界 |
|---|---|---|
| 外层立规者 `outer.legislator` | 制定外层规则、接口承诺、验收、预算分配；受理规则复议 | 不向内层派工、不接受代码、不修改用户意图 |
| 外层执行者 `outer.executor` = 内层指挥者 `inner.coordinator` | 自主领取外层就绪任务，拆分派工、内部技术裁决、内层接受、集成发布 | 不能改外层规则、自批外层验收或任免外层同席 |
| 外层裁衡者 `outer.arbiter` | 独立审查规则与用户意图是否一致、整体成果是否符合有效规则 | 不是内层下属；不派工、不接管实现，不受内层指挥者撤换 |
| 内层执行者 `inner.executor` | 按指挥者派工实施、自测、报告精确成果 | 不自行抢外层任务或再创建团队 |
| 内层审查者 `inner.reviewer` | 独立技术取证，向指挥者报告事实与建议 | 不自审；其 PASS 不代替外层裁衡 |
| 内层监督者 `inner.supervisor` | 监督内层执行者／审查者的行为和指令理解，向指挥者报告 | 不监督指挥者或外层三席，不替代技术审查或批准发布 |

除执行者＝指挥者这一桥接关系外，完整模式各席不兼任。内层作者、指挥者不能兼任外层裁衡者；外层裁衡者也不兼任内层审查者。独立角色可以复用经核对的原始证据，不能复用他人的签名冒充自己的判断。（COM-02、COM-04）

## 执行流程

1. **外层立约。** 立规者保留人类意图来源、制定版本化契约；执行者反馈可行性；裁衡者审查权限、意图一致性和可验证性。满足分权协议 SEP-02 才生效。内层资源安排属于执行者权力，不能改变外层验收。
2. **桥接与派工。** 执行者自主领取外层 READY 任务，将该任务映射为内层计划与任务。登记上下层 ID、外层契约版本、内层计划版本、共享任期、允许路径和预算子额度。指挥者只在这些边界内签发集权指令，接收者确认目标、禁止项与验收。（COM-03）
3. **内层实施。** 指挥者组织实施、独立审查与下属监督，分别保存原始记录。明确每项任务唯一 owner 和写入路径；提醒所有实现者共享工作区、保留他人修改。冲突路径串行，独立路径可并行；工作副本不等于安全隔离。
4. **内层接受。** 审查、必需监督和硬门槛满足后，指挥者记录 `INNER_ACCEPTED`。保留失败与异议；普通建议按授权处置。此状态仅表示内层管理接受，不表示外层验收或发布权限。（COM-04）
5. **候选与外层裁衡。** 指挥者在获准工作区准备精确集成候选；新增逻辑、配置或冲突修复先完成必要内层重验，再提交外层裁衡。裁衡者核对意图、有效规则、候选及证据，形成自己的结论；通过后标记 `OUTER_VERIFIED`。不得要求候选在生成前就已验收。（COM-04）
6. **统一交付。** 同一执行者／指挥者核对内层接受、外层裁衡、精确版本、当前身份任期、无阻塞异议、预算和适用用户授权后执行合并／发布。一个真实动作关联两层记录，只记一次副作用和回执。`INTEGRATED`、`RELEASED` 分别据实报告。（COM-05）
7. **阶段复盘。** 执行者汇总内层耗时、返工、监督与协调成本；裁衡者评估质量和意图保障；立规者提出保留／简化／改规建议。复盘不自动改规、不增设交付批准，沿用分权 SEP-09。

## 停止与升级

外层规则偏离人类意图或成果被裁衡阻塞时，内层管理 ACCEPT 不能放行。指挥者可申请外层立规者复议规则；事实误判走裁决复核；拟调整人类意图由立规者向人类提出具体建议，取得明确同意后改规重审。仅暂停受影响范围。（COM-07）

外层任何一席失联，停止新契约生效、最终验收、新合并和发布；内层指挥者失联即同一外层执行席失联，同时使旧内层命令失去新增行动依据。替换必须符合外层获准机制，并同步更新桥接身份、任期和内层指令，不能由下属选举继任。（COM-08）

角色缺失、预算耗尽、工具不支持或证据缺失时，继续获准且不受阻塞的本地准备工作，明确记录 `INCOMPLETE_COMPOSITE` 及具体等待项。不得用单会话换称呼、递归扩容、停掉外层同席或让裁衡者兼审查者来伪装完整模式；也不静默切换原有模式。（COM-06）

## 交付格式

依次报告：**实际模式与能力 → 外层三席和内层团队身份／共享任期 → 有效契约与桥接关系 → 精确成果 → 内层审查、监督和接受 → 外层独立裁衡及异议 → 实际集成／发布回执 → 全链路消耗 → 复盘与未解决事项**。

未执行检查写“未执行”；缺独立审查记 `AWAITING_INDEPENDENT_REVIEW`，缺必需监督记 `AWAITING_SUPERVISION`，缺外层席位记 `AWAITING_ROLE_REPLACEMENT`。本地草案可交付审阅，不冒称完整团队验收。无异步工具不承诺后台继续。

## 常见误区

- 把“外层执行者＝内层指挥者”拆成两个人，增加一道无依据的管理层。
- 把外层裁衡者当内层审查者的上级，或当可被指挥者撤换的下属。
- 用内层 PASS／ACCEPT 覆盖外层异议，或让外层通过抹去内层真实硬失败。
- 以新建子任务重置预算，或对同一部署由两层重复执行。

维护本技能时可使用 [行为场景](evals/scenarios.json) 检查衔接决策。场景是待运行输入，不是已通过证据；静态检查与文字探针均不证明真实六身份协作、权限强制或部署已运行。
