# 分权开发模式技能

**立规有界，执行自主，裁衡独立。** 固定三类平级、独立职能：**立规者、执行者、裁衡者**，分别行使规则制定权、工程执行权、独立裁决权。人类确定目标与授权边界，三者在其内相互制衡，不设指挥者或监督者。执行者数量为 N≥1，用户可明确指定；默认 N=1，实际治理团队为 1 名立规者、N 名具名执行者和 1 名裁衡者，共 N+2 个真实子 agent。

借鉴美国三权分立的职能分离与制衡原则，具体流程是工程适配。目录与技术标识保留 `gas-decentralized-development`。本 Skill 提供协作协议，不自带运行器、权限隔离或发布服务；不自动扩大用户授权或切换模式。

## 启动与适用边界

读取 [完整协议](references/protocol.md) 与 [运行证据规范](references/runtime-evidence.md)。组建前仅核对创建与展示能力、已有的人类输入和授权，明确 N+2 个子 agent 的完整名单及执行者数量来源；不检查业务项目或开展技术分析。全部满足 TEAM_READY 后，由对应治理子 agent 检查真实项目、已有修改、验证入口及业务工具与授权适用性。适合希望分离定规、实施和验收权的任务；就绪后接口不清时由各席先形成契约，冲突路径上的实施串行进行。

启用本模式时，在宿主允许范围内建立 N+2 个独立子 agent，分别承载立规、执行与裁衡；主会话不占席。默认配置为 3 个治理子 agent 加 1 个展示主会话；N>1 时增加的成员均属执行职能，不增指挥或监督职能，不递归创建 agent。执行者数量和完整名单按 AGENT-01 确认，宿主槽位不足时等待，不擅自缩减用户指定人数。主会话仅展示原始事实、进展和人类输入，并作宿主必要的机械转接；不得立规、选择或分配业务、实施、裁衡或发布。单会话换称呼不能冒充三方独立。

复用已有有效批准。完整名单中的 N+2 名治理子 agent 全部满足 TEAM_READY 后，由各席推进授权内工作。记录真实能力，worktree 只隔离副本，不是安全沙箱。缺少子 agent 能力或席位时按 FALLBACK-01 保持等待，主会话不代行或降级实施。

## 子 Agent 创建前的人类交互（AGENT-01）

每次新建、增补或替换子 agent，必须依次完成“配置弹窗 → 职责弹窗 → 人类明确答复 → 创建”。适用于所有角色及组合模式的内外两层；启用模式、已有开发授权或常规派工授权不能代替本次选择。可以批量展示，但必须逐个列出 agent，允许分别修改。不得先创建再补问。

1. **核对可用能力。** 核对当前创建工具和宿主角色配置支持的模型、推理强度及其兼容性，不照抄历史型号，不虚构选项。子 agent 的服务档位沿用父 agent，不列为独立可配置能力。
2. **配置弹窗。** 使用客户端原生交互提问工具；当前支持时优先使用 `functions.request_user_input_async`，其他工具仅在其当前模式与用途允许时使用。分项提供模型、该模型支持的推理强度选项，标出推荐项并允许自由回答；选项数量超过界面限制时分批展示。人类改变模型后重新核对强度兼容性。不再询问服务档位／速度，也不提供子 agent 的默认／Fast 选择。
3. **保持活跃并等待。** 每次配置弹窗、职责弹窗和修改后再次确认，都进入下述“等待人类”流程。等待期间整个任务停在当前交互步骤，连不依赖该 agent 的后续工作也不推进。不兼容或不可用的选择须说明原因并重新提供可用选项，不静默替换。
4. **职责弹窗。** 配置确定后，再通过弹窗逐个展示 agent 的名称／角色、所选配置、目标、负责模块或路径、具体职责、交付物、验收标准和权限边界。提供“按当前职责创建”“修改职责后再确认”“取消创建”选项，并明确可直接自由输入职责修改。收到修改后更新职责并再次展示；只有人类明确接受最终版本才可创建。涉及模式角色边界冲突时说明冲突并由人类决定调整方案，不暗中改动模式。
5. **按最终选择创建。** 创建调用和任务提示必须与最终答复一致，通过当前接口支持的字段或获准的配置机制传递模型、推理强度；服务档位沿用父 agent，不添加独立覆盖。若显式覆盖配置与完整历史继承不兼容，使用接口允许的有限／空历史并在任务提示中补齐必要上下文。给实现者明确文件所有权，并说明共享工作区、保留他人修改。创建失败后若需改变配置或职责，重新弹窗，不擅自降级。
6. **记录与限制。** 在运行记录中保留每个 agent 的配置选择、最终职责、人类答复引用、实际创建参数、返回身份及未能验证的设置；尚未创建时不填虚假身份。原生弹窗不可用时，说明缺失并暂缓创建，等待交互能力恢复或人类明确允许替代方式；普通聊天说明不能冒充已完成弹窗。收到取消则不创建。此规则不为已创建 agent 在已确认职责内的普通后续派工增加审批。

### 运行位置：默认在 Codex 子 agent 列表展示

**所有子 agent 默认使用 Codex 客户端原生子 agent 创建与管理通道，并在当前任务的子 agent 列表中展示。** 本条约束 agent 会话的承载方式；agent 正常调用终端做构建、测试或其他工具操作不属于“放到 CLI 运行”。

- **原生列表优先。** 创建前核对原生子 agent 工具、角色加载与父子会话关联；创建后核对目标身份与客户端可发现记录。独立自定义角色配置优先用于原生角色，不因创建工具缺字段或加载失败直接改用 `codex exec` 等独立 CLI 会话、后台进程或终端脚本托管 agent。普通聊天中列出名称、打开终端标签或另建普通会话，都不能冒充子 agent 列表展示。
- **需要 CLI 时先弹窗。** 在启动任何 CLI agent 前，必须通过客户端原生弹窗说明受影响角色、具体理由、已尝试的列表方式、CLI 的展示和管理差异，以及预期运行范围；提供“同意本次 CLI 运行”“不同意，继续尝试子 agent 列表”“暂停／取消创建”，允许自由回答。等待期间沿用保持活跃、不推进任务的规则。没有弹窗或未回复时不得启动，超时也不算同意。
- **人类同意。** 仅在答复覆盖的角色和范围内使用 CLI，继续遵守已确认的模型、强度、职责、预算和全员就绪要求；不能把一个角色的同意扩大到全部团队。启动前在 Codex 客户端明确说明实际运行位置，创建后报告真实会话／进程身份、状态查看方式和控制入口，不声称已进入原生列表。
- **人类不同意。** 保留拒绝记录，继续尝试原生列表路线，检查角色注册与重载、配置作用域、所选角色、父子关联、工具返回错误及可用的原生重试／恢复方式；对已发现原因做相应修正，不以同样参数反复失败代替排查。不得因一次失败、等待较久、操作方便或角色配置麻烦立即切换 CLI。
- **确实只能 CLI 的最终兜底。** 只有已取得前述弹窗答复、用户不同意后仍完成了当前环境适用的列表路径排查／修复／重试，并有可核对证据表明列表方式无法实现而 CLI 可行，才可按本规则的条件性兜底授权使用 CLI；无需把此前拒绝篡改成同意。启动前必须在 **Codex 客户端主会话** 明确列出失败证据、为何只能 CLI、将使用 CLI 的角色及查看／停止方式，运行记录注明“列表路径不可用后的 CLI 兜底”。未尝试或未知能力不能算不可能。用户若进一步明确“即使只能 CLI 也禁止使用”、要求暂停或取消，则服从该最新指令，保持等待，不启用兜底。
- **未就绪不得推进。** 原生路径须有可核对的列表关联／展示证据；CLI 路径须满足本条同意或严格兜底条件并已在客户端披露。把运行位置、实际身份、展示验证状态及弹窗答复计入完整团队就绪核对。无法确认列表展示或 CLI 条件未满足时保持 `WAITING_FOR_TEAM`，不虚构已显示、已同意或全员就绪。
- **能力边界。** 宿主硬性权限、并发和预算限制不因改用 CLI 失效；不得通过 CLI 绕过它们。本技能规定创建决策与披露流程，不能把未被客户端支持的 CLI 会话强制塞进原生列表。

### 全员就绪后统一启动

**所有计划中的子 agent 没有全部创建并就绪之前，禁止推进任务。** 本规则适用于集权、分权和组合模式；组合模式须同时覆盖外层与内层，不能仅外层建齐就开始工作。

- **先确定完整名单。** 创建前登记本轮全部角色、子 agent 数量及职责版本，逐个完成配置与职责弹窗确认。禁止把尚未创建的必需角色挪到“以后再建”以规避等待。名单如需删减或职责调整，须由人类明确确认，不能因创建失败自动缩减团队。
- **逐个创建，全部待命。** 每个创建提示都必须明确：“当前仅确认身份、配置与职责，回复就绪并等待全员就绪通知；不得开始任务执行。”创建调用成功返回真实身份且该 agent 已确认职责并报告就绪，才记为该成员创建完成；已发出调用、排队中、身份未知或尚未回复均不算。先创建好的子 agent 不能提前分析业务、改文件、测试、审查或发布。
- **只允许组建动作。** 屏障关闭期间，主会话和已创建的子 agent 仅可处理人员名单、配置选择、职责确认、创建／重试、就绪回执及必要的等待和状态记录，不推进任何业务任务，包括不依赖缺席成员的工作。组合模式中负责内层团队的执行者可以继续完成内层创建，但不能开始外层或内层业务工作；任一弹窗待答时仍按“等待人类”流程停在该步骤。
- **核齐后统一启动。** 按完整名单核对所有真实身份、最终确认记录和就绪回执，全部满足后才记录 `TEAM_READY`，向各成员发送对应名单与职责版本的启动通知，并进入业务流程；无需额外再问一次批准。该通知只是全员就绪事实，不改变三种模式原有的派工权与平级关系。任一成员失败、未确认或不可用时保持 `WAITING_FOR_TEAM`，不以其他成员就绪、时间已到或局部任务独立为由放行。
- **增补或替换重新等待。** 运行中决定新增或替换成员时，关闭全员就绪屏障并通知现有成员在最近安全点停住，不开启新的业务动作；允许正在进行且不能安全中断的动作到安全点，并如实记录。新名单全部创建并确认就绪后再统一恢复，不强杀进程制造“已暂停”。本规则优先于技能和协议中“继续不受影响工作”的一般条款；工具无法实现待命与统一恢复时报告限制并保持未就绪，不虚构屏障已生效。

### 服务档位：沿用父 agent

子 agent 的服务档位（速度）沿用主会话／直接父 agent，不提供独立选择、配置或切换。不为单个子 agent 注入 `service_tier` 覆盖，不通过自定义 TOML、角色注册、重建会话或 CLI 为其单独设置 Fast／默认档位，也不自行修改父会话或全局档位。

取消服务档位专用弹窗、配置路径排查及回执核验要求；不把服务档位验证计入成员就绪或 TEAM_READY 前提，不因缺少档位参数／回执而阻塞创建和任务。模型、推理强度仍须由人类选择；职责确认、等待、全员就绪、客户端列表优先与 CLI 例外规则保持不变。

### 等待人类：保留弹窗，保持任务活跃，不推进

- **思考时间。** 每个弹窗默认预留至少 **30 分钟**，人类可指定更长时间。30 分钟是思考窗口，不是自动取消期限；届满仍未答复就延续等待。人类提前答复则立即处理，不必等满时长。
- **真正等待。** `functions.request_user_input_async` 返回只代表问题已发出，不代表用户已回答。保留同一待答弹窗；随后使用当前可用、能被新用户消息唤醒的等待工具。在支持 `clock.sleep` 的宿主中，每次调用 `clock.sleep({duration_ms: 60000})`，返回后检查实际用户消息，未取得本轮有效答复就再次等待。每轮最多 60 秒，避免一次长阻塞；工具返回、一次等待超时或无关消息均不解除等待。
- **禁止结束或越过。** 不因用户暂未点击发送 `final`、标记任务完成、自动取消、收起／替换弹窗，也不创建 agent、继续派工、实施、验收或发布。不用“等你答复”作为结束任务的最终答复；可以按宿主要求发送简短的等待状态说明，但不催促、不改变问题、不反复重开弹窗。这里的等待约束优先于本技能其他“继续不受影响工作”的一般规则。
- **有效答复。** 只接受针对当前问题的人类实际提交；预选、空答、未回复、过往选择均不算。仅回答部分配置时保留已答项，继续收集缺失项；“我还在想”“继续等”延长等待，无关消息不当成配置或职责确认。人类明确取消、暂停或改变任务时按其新指令处理；修改职责后对最终版本重新确认。
- **能力与恢复。** 不向提问工具添加不存在的超时或保活参数，不用忙循环、后台进程或定时任务冒充前台等待。当前工具无法设置客户端弹窗保留时长；技能约束的是 agent 的等待行为，不能保证界面持续显示或绕过宿主硬性时限／预算。若宿主确实强制中断，保存待答问题、已选配置和职责版本，记录 `WAITING_FOR_HUMAN` 而非完成；说明实际限制，恢复后从该步骤继续，已收到的有效答复不重复索取。仅确认旧弹窗已失效时才重新展示。

## 权责边界

| 主体               | 专属职责                                     | 制衡与边界                                  |
| ---------------- | ---------------------------------------- | -------------------------------------- |
| 人类用户             | 确定目标、授权、预算及硬门槛；解决超授权或持续僵局                | 在治理团队之外；已有适用授权无需重复批准               |
| 立规者 `legislator` | 制定契约、接口与验收；受理规则复议，必要时向人类建议调整意图           | 规则接受意图一致性审查；未经人类明确同意不改变其意图；不验收代码、不集成发布 |
| 执行者 `executor`   | 各自负责具名独立模块开发、测试/验证代码、该项验证、执行监控上报及获准集成发布                   | 对裁决不满可向立规者申请规则复议；不能自行改规、自批或绕过裁决        |
| 裁衡者 `arbiter`    | 审查立规者的规则是否符合人类意图，同时审查执行成果；分析执行输出与可用监控证据，对偏离规则提出异议并要求修改 | 不代替人类决定意图或立规者改规；不编写/修改测试验证代码，证据缺口退具名执行者补齐；可复跑现有命令        |

三类职能及 N+2 名子 agent 无上下级，不兼任另一权力职能。各执行者协商独立任务、开发文件、验证文件及共享资源归属；在全员就绪且所有权和依赖核对后，尽可能并行全部就绪独立任务，冲突资源串行。任一执行者不能指挥其他平级执行者；立规者也不取得派工权。主会话不进入治理名单；展示与机械转接不产生治理权。登记、日志和 CI 是工具职责，不是第四治理席。真实身份、任期与权限记录在 [运行契约](templates/run.example.json)。（AUTH-02、DEC-03、SEP-01）

## 三项制衡路径

1. **规则也接受裁衡。** 裁衡者既审查执行成果，也审查立规者制定的规则是否忠实于人类的目标、约束和明确偏好。即使实现完全符合规则，规则本身偏离人类意图仍应提出异议，说明偏离之处，要求立规者修改后重新接受审查。（SEP-06）
2. **执行者可以申请规则复议。** 执行者不满裁决时，可请立规者重新审视相关规则是否合理、是否需要修改；不必先证明裁衡者判错。立规者说明维持或修改的理由，修改后的规则仍须由裁衡者审查。申请复议不自动撤销原裁决，也不允许两者联手绕过裁衡。（SEP-07）
3. **意图变更由人类决定。** 立规者认为规则合理，但裁衡者判定其偏离人类意图时，可以向人类提出调整意图的建议，说明原意图、拟调整内容、理由与影响。只有人类明确同意后，才能在同意范围内更新意图依据和规则；人类不同意则不得修改意图，应按原意图修正规则。未答复或答复不明确不视为同意。（SEP-08）

## 执行流程

1. **立约。** 立规者依据人类意图制定范围、接口、结构化验收条目、预算与版本，并保留意图来源；执行者在 TEAM_READY 后按授权内有限试验许可，以适用关键路径小样本反馈可行性，可复用有效环境证据；裁衡者审查意图一致性、授权边界与可验证性。核对齐全、无阻塞异议的授权内契约生效；意图变更按 SEP-08 取得人类明确同意。不为局部动作反复会签。（AUTH-01、CHANGE-01、SEP-02）
2. **自主实施。** 每名执行者按 [任务契约](templates/task.example.json) 协商并认领独立模块，同时承担该项开发、测试验证代码及实际验证，记录具名开发/验证归属和监控事实。默认一个执行者，公共登记用单写工具；多执行者尽可能并行全部就绪且无冲突的独立任务，普通 JSON 先读后写不算原子认领。（DEC-01、DEC-02）
3. **提出异议。** 用 [异议记录](templates/dispute.example.json) 区分规则偏离意图、执行者申请规则复议、裁决事实复核。前两类由立规者回应规则是否需修改；裁决事实争议按 SEP-03 处理。涉及调整人类意图再由立规者提出具体建议，请人类决定；仅冻结受影响范围。（SEP-06、SEP-07、SEP-08）
4. **独立裁衡。** 裁衡者沿“人类意图 → 条款 → 检查”覆盖矩阵，分别记录“规则是否符合人类意图”和“实现是否符合有效规则”，补充实际方法独立性；分析执行者输出和可用监控证据，不编写或修改测试/验证代码。缺证据时按任务退具名执行者补齐；可复跑现有检查命令，保留原结果，仍独立判断精确候选。规则偏离时退回立规者，不能仅因实现合规而放行，也不能把规则缺陷全部算成执行者错误。规则或意图获准更新后，重审规则并重验受影响成果，不把旧失败改写为通过。（EVID-01、EVID-02、SEP-06）
5. **集成发布。** 执行者准备精确集成候选，裁衡者验证该版本；生效契约、有效独立评审、适用用户授权三项同时满足后，执行者合并或发布，填写 [交付记录](templates/release.example.json)。已有发布授权直接复用，技术通过不能替代它。（SEP-04）
6. **据实交付。** 分别报告 `VERIFIED`、`INTEGRATED`、`RELEASED`，保留各方意见、精确产物、验证记录与真实回执。三方同意不等于正确性证明。（EVID-02、FALLBACK-01）
7. **阶段复盘。** 在约定阶段或最终交付节点，三方简短回顾规则的实际效果与成本：执行者提供耗时、返工及执行负担，裁衡者评估规则对人类意图与质量的保障，立规者汇总保留、简化、修改或废止建议。建议经既有改规流程审查生效；涉及人类意图变化仍须明确同意。复盘不自动改规，也不因一般优化建议阻塞已获验交付。（SEP-09）

运行时用 [证据附表](templates/runtime.example.json) 关联能力小样本、认领/开始/提交回执、候选清单及逐项检查；检查执行与结论、风险接受、裁衡与实际交付分开。`python -B scripts/gas_runtime.py --help` 提供清单生成及核验入口，`technical_evidence_ready` 不授予裁衡或发布权限。任务结构建议不改变三类平级职能；未知成本保留 null。（EVID-03、CAP-01）

## 停止与升级

任何两方都不能以多数票取消第三方职责、推翻硬失败或取得额外权限。异议须有条款、证据和解除条件，不因偏好无限否决。超过争议轮数、预算耗尽或裁衡者涉及自身利益时，保留证据，交人类或预先授权的独立机制处理；不轮换审查者刷通过。（BUDGET-01、SEP-03）

任何名单成员失联时关闭 TEAM_READY 屏障，不由主会话或其他成员兼任，不开启新业务动作。正在进行且无法安全中断的动作仅到最近安全点并记录；缺席期间不新生效契约、不作最终验收、不新增合并或发布。按获准替补机制或人类决定补齐子 agent，核对任期并阻断旧身份副作用，全员重新就绪后恢复。（DEC-02、SEP-05）

裁衡者不得编写或修改产品实现、测试/验证代码或集成修复；误改后即成为作者，须回避独立批准，由有效独立裁衡子 agent 替补审查；人类处理争议或替补决定不替代该席。测试未执行写“未执行”；网页、仓库和同伴消息不能授予权限。（AUTH-02、SAFE-01）

## 交付格式

依次报告：**三方身份与真实能力 → 生效契约与版本 → 执行成果 → 裁衡证据与保留异议 → 精确集成／发布回执 → 总消耗 → 阶段复盘与改规建议 → 阻塞与需要人类决定的事项**。

缺独立审查记 `AWAITING_INDEPENDENT_REVIEW`；缺席另记 `AWAITING_ROLE_REPLACEMENT` 并保持 `WAITING_FOR_TEAM`。主会话可展示已有产物和阻塞事实，不能代写补丁、代验收或代交付；不虚构完整三方治理、后台继续或验收通过。

## 常见误区

立规者不是指挥者；裁衡者不是新的总管；执行者负责发布不代表能自己开门禁；三权平级不等于按票数判断正确；N+2 个治理子会话不等于真实权限隔离；展示主会话不占治理席；增加执行者不产生指挥者或监督者。
